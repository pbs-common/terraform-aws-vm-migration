TECHNICAL RATIONALE: WHY 2008 R2 REQUIRES ATTENTION
================================================================================

Windows Server 2008 R2 is 15+ years old and has known constraints:

1. AWS MGN SUPPORT STATUS
   ✅ SUPPORTED by AWS Transform (but flagged as end-of-life)
   ✅ Uses LEGACY INSTALLER: AwsReplicationWindowsLegacyInstaller.exe
      (separate from standard agent installer due to older software components)
   ✅ Nitro instances supported for 2008 R2 and up

2. PRE-MIGRATION PREREQUISITES (CLIENT RESPONSIBILITY - MUST BE VALIDATED)
   ⚠️ .NET Framework 4.5 or above installed
   ⚠️ Service Pack 1 (SP1) installed
   ⚠️ KB updates for SHA-2 Code Signing Support (MOST COMMON FAILURE POINT)
      → Without SHA-2, replication agent driver won't install
   ⚠️ WMI service must be active
   ⚠️ System drive must use MBR partition scheme (GPT NOT supported)

3. POST-MIGRATION OS STRATEGY
   • Rehosting 2008 R2 as-is = lift-and-shift, no modernization
   • OS remains end-of-life on EC2
   • Client should plan follow-on OS upgrade or app refactor after landing

4. TRANSFORMATION COMPLEXITY
   • Older .NET Framework versions may not containerize well
   • Application-layer dependencies on legacy OS features
   • Custom application modifications may be needed post-migration

   - Document any servers that fail pre-flight → escalate to AWS team

✅ Discovery
   - Transform auto-discovers validated 2008 R2 servers in network scan

✅ Wave Planning
   - Transform analyzes all 30 servers together for optimal wave sequencing
   - Considers application dependencies (Alliant/BizTalk/ScheduAll)
   - Groups dependent servers (db + app + terminal services) in same wave
   - Instance-type recommendations account for Nitro compatibility

✅ Bulk Rehosting
   - MGN Connector coordinates replication using legacy installer
   - Transform manages test/launch phases for all 30 servers in parallel
   - Post-migration: Client owns OS upgrade strategy

WHY TRANSFORM (not MGN console direct)?
   ✓ Loses no wave planning logic; all 30 servers coordinated at scale
   ✓ Agentic discovery/grouping (vs manual by 3-person team)
   ✓ Meets "far less manual effort" requirement for 89-host migration
   ✓ Pre-conditions are validation, not blockers (Transform handles agents)
   ✓ Application dependencies handled efficiently at scale
