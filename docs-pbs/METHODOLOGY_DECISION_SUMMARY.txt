================================================================================

PROJECT CONTEXT
- 93 total servers across inventory; 49 being migrated (Strategy = "rehost")
- 44 servers on HOLD (business reasons, not migrating in this scope)
- 3-person migration team
- AWS team owns landing zone, TGW, and inspection architecture
- Wave planning and host discovery already completed via mapplanner
- Approach: Use AWS Transform MGN's agentic workflow for bulk rehosting orchestration
  (agent coordination, parallel deployment, built-in gates) while respecting AWS team ownership

================================================================================
FINDINGS & DECISIONS
================================================================================

CORE METHODOLOGY DECISION
├─ Choice: AWS Transform MGN agentic workflow (vs MGN console direct)
├─ Scope: Import existing wave plan (already validated); skip discovery/re-planning
├─ Primary Value: Bulk rehosting orchestration + de-risking legacy Windows fleet
│
├─ Why Agentic Orchestration?
│  • Coordinated orchestration of 49 server rehosting across waves (vs manual timing)
│  • Built-in approval gates with human-in-the-loop pauses (vs custom workflow)
│  • Unified monitoring dashboard for all 49 servers (vs per-server console checks)
│  • Self-registration path: simple client-independent agent deployment
│    (Servers auto-register in console when agent connects; no pre-matching needed)
│  • Particular strength: Managing prerequisites + validation across 3 Windows 2008 R2 servers
│  • Approved approach: Transform confirms self-registration works well for manual deploys
│
└─ What This Is NOT
   • Not a re-discovery initiative (mapping already done)
   • Not a re-planning initiative (waves already validated)
   • Not a rollback/safety difference (MGN engine has both paths)
   • Not a network/landing-zone simplification (those remain AWS team owned)
   • Not incompatible with manual agent install (agentic workflow remains after manual deploy)

FINDINGS & DECISIONS (DETAILED)
================================================================================

1. NETWORK CREATION SUPPRESSION ✅
   ├─ DECISION: Use "Discovery and server migration" migration scope
   ├─ EFFECT: Excludes "Migrate network" phase entirely
   ├─ RESULT: No VPC/subnet/security-group generation by Transform
   ├─ AWS TEAM RETAINS: Network topology, TGW, inspection architecture design
   └─ EXPLICIT STATEMENT: "Transform migration scope explicitly excludes network 
      migration phase. The AWS team retains full control over Transit Gateway 
      and inspection architecture design."

2. LANDING ZONE SETUP ✅
   ├─ FINDING: AWS Transform VMware workflow does NOT include landing zone setup
   ├─ HOW IT WORKS: Transform deploys into target account CLIENT provisions
   ├─ TARGET ACCOUNT CONNECTOR: Configured by AWS administrator before job runs
   ├─ RESULT: Landing zone is inherently client-owned—nothing to "suppress"
   └─ NOTE: Not a configuration decision; manual/owned by design

3. APPROVAL GATES ✅
   ├─ APPROACH: Transform provides several built-in human-in-the-loop checkpoints
   ├─ NO EXTERNAL TOOLING NEEDED: Workflow pauses automatically at approval points
   ├─ KEY GATES (scope-dependent; list reflects "Discovery and server migration" scope):
   │  1. Wave Planning → "Confirm the wave plan" (CSV review/customization/re-upload)
   │  2. Inventory → "Confirm inventory" (instance-type review)
   │  3. Target Account → "Get approval from AWS administrator" (explicit gate)
   │  4. Wave Prep → "Review migration waves" (pre-execution checkpoint)
   │  5. Cutover → "Mark applications ready for cutover" (final gate)
   │
   ├─ RESULT: Built-in pause-review-approve cycle keeps stakeholders in control 
   │           at each major decision boundary
   │
   └─ NOTE: Exact gate count varies by scope chosen; this reflects your config
