================================================================================
TECHNICAL RATIONALE: WHY 2008 R2 REQUIRES ATTENTION
================================================================================

Windows Server 2008 R2 is 15+ years old and has known constraints:

1. AWS MGN SUPPORT STATUS
   ✅ SUPPORTED by AWS Transform (but flagged as end-of-life)
   ✅ Uses LEGACY INSTALLER: AwsReplicationWindowsLegacyInstaller.exe
      (separate from standard agent installer due to older software components)
   ✅ Nitro instances supported for 2008 R2 and up

2. PRE-MIGRATION PREREQUISITES (CLIENT RESPONSIBILITY - MUST BE VALIDATED)
   ⚠️ .NET Framework 4.5 or above installed
   ⚠️ Service Pack 1 (SP1) installed
   ⚠️ KB updates for SHA-2 Code Signing Support (MOST COMMON FAILURE POINT)
      → Without SHA-2, replication agent driver won't install
   ⚠️ WMI service must be active
   ⚠️ System drive must use MBR partition scheme (GPT NOT supported)

3. POST-MIGRATION OS STRATEGY
   • Rehosting 2008 R2 as-is = lift-and-shift, no modernization
   • OS remains end-of-life on EC2
   • Client should plan follow-on OS upgrade or app refactor after landing

4. TRANSFORMATION COMPLEXITY
   • Older .NET Framework versions may not containerize well
   • Application-layer dependencies on legacy OS features
   • Custom application modifications may be needed post-migration

DECISION: HOW 3 WINDOWS 2008 R2 REHOST SERVERS FLOW THROUGH TRANSFORM
================================================================================

AWS Transform's agentic workflow COORDINATES these 3 servers through bulk 
rehosting with SELF-REGISTRATION and ORCHESTRATION:

✅ Pre-Requisite Validation (CLIENT responsibility - BEFORE agent install)
   - Audit all 3 servers for prerequisites:
     • .NET Framework 4.5 or above installed
     • Service Pack 1 (SP1) installed
     • SHA-2 KB updates applied (MOST CRITICAL for agent installation)
     • WMI service is active
     • System drives use MBR (not GPT)
   - Test target network access from client servers (agent outbound connectivity)
   - Document any failures → escalate to AWS team before proceeding

✅ Agent Installation & Self-Registration (CLIENT responsibility)
   - Use AWS Transform's "Deploy replication agents on your own" path
   - SSH/RDP to each of the 3 servers
   - For 2008 R2 servers: Use legacy installer (AwsReplicationWindowsLegacyInstaller.exe)
     (Different from standard installer due to older OS components)
   - Run installer: servers automatically self-register in Transform console
     (No need to pre-match user-provided-ids; servers appear automatically)
   - Once agents installed:
     • Servers appear in Transform MGN console within minutes
     • Ready to be assigned to applications/waves

✅ Wave Assignment & Orchestration (YOUR TEAM)
   - Assign 3 servers to their respective waves (already planned in mapplanner)
   - Import wave plan CSV to Transform (bulk-assign to applications/waves)
   - Transform manages orchestration across all 3 servers:
     • Unified replication status monitoring (single pane for all 3)
     • Coordinated test phase (launch all 3 test instances together)
     • Approval gates enforce review before cutover
     • Coordinated cutover across wave dependencies

WHY AGENTIC ORCHESTRATION (not MGN console direct)?
   ✓ Self-registration simplifies deployment (servers auto-discover when agent connects)
   ✓ Unified monitoring dashboard (single pane for all 3 servers' status)
   ✓ Prerequisite validation tracked via approval gates (not manual checklists)
   ✓ Coordinated cutover across wave dependencies (vs manual per-server timing)
   ✓ De-risks legacy OS fleet through structured orchestration + gates
   ✓ Built-in approval workflow (no custom Jira/email processes needed)

KEY INSIGHT - SELF-REGISTRATION PATH:
   • Simpler than pre-matching: No need to extract user-provided-ids before install
   • Servers automatically register when agent connects to Transform service
   • Just group/assign them in Transform UI after they appear
   • No risk of duplicate entries (unlike pre-matching + self-reg mixed together)
   • Cleaner workflow for client-independent agent installation
